# TripSplit — product and engineering plan

> Engineering rules live in [`../CLAUDE.md`](../CLAUDE.md). The daily cheat sheet is
> [`../AGENTS.md`](../AGENTS.md). This document says **what** we are building and **why**, and
> how the work is cut for a 48-hour hackathon.

## 1. Product

**TripSplit — "from group chat to tickets".**

An agent joins a group of friends and walks them through the whole trip: it proposes three
ready-made packages, collects votes, collects each person's share, books (train, stay,
activities) and watches the trip to the end — a delay becomes a rebooking and a re-split.

### Why

The "are we going somewhere?" thread dies because nobody wants to decide and nobody wants to
front the money for everyone. Group travel apps (Tripti, Troupe, FlowTrip, Wanderlog,
Splitwise) do votes and splits, but none of them **buys** for the group. Meta Muse books
flights and hotels for one person only. The AI travel startups that failed all *planned* and
never let you *buy* — we target exactly that missing step.

### Edge

1. **Nobody fronts the money.** Each member pays their own share; the booking fires only when
   everyone has paid.
2. **Post-purchase care.** A delayed train or a member dropping out means a rebooking and an
   automatic re-split, not a new group chat.

### Risks

| Area | Risk | Mitigation |
|---|---|---|
| Legal | Collecting money and bundling services likely makes us a tour operator or a "linked travel arrangement" provider in Poland: registry, financial guarantee, TFG fee up to 30 PLN/person | Consult a lawyer before any real money moves; the demo uses a fake payment provider |
| Agent fragility | Supplier sites change, anti-bot measures, CAPTCHA, terms of service | Per-supplier playbooks, trajectory cache with self-healing, human handoff instead of bypassing gates |
| Market | Consumer travel startups pivot to B2B, get acquired or die; CAC is high and trips are rare | Narrow entry niche, distribution through existing groups (an invite link spreads itself) |
| Business model | Subscription does not fit an occasional purchase | Per-trip fee plus supplier commissions |

### First step

A narrow scenario: a weekend city break for 4–8 people from Poland, or stag/hen parties.

**48-hour demo:** six people, a weekend in Prague. The agent proposes three packages, the group
votes, each member pays, the agent books the train and the stay live, and the final scene is a
delayed train followed by a rebooking.

**Where to show it:** START Hack League Munich (21–22.11), hackaTUM (27–29.11).

### Open questions

- **Group assistant vs full organizer.** Everyone pays the suppliers directly (assistant) or we
  bundle and take a margin (organizer, with the legal weight that carries).
- **Product surface later.** A WhatsApp/Messenger bot is the natural home; for the demo it is
  our own web app.
- **Starting niche.** City breaks or stag/hen parties first.

## 2. Decisions taken (2026-10-31)

| Decision | Reason |
|---|---|
| Own web app, not a messenger bot | WhatsApp/Messenger Business APIs need approval we cannot get in 48 hours |
| Booking agent = Python port of a field-tested browser harness (Camoufox + Playwright + LLM planner with vision), living in `backend/src/app/agent/` | Known to work; stays inside the backend's layering as infrastructure at the edge |
| Skeleton rigor kept for layers, types, the OpenAPI bridge and auth; contract tests relaxed and CI on `workflow_dispatch` during the hackathon | Structure pays off immediately, gates on every push do not |
| Payments are the LAST step: a `PaymentProvider` port with a `FakePayments` adapter first, Stripe later with no domain changes | The money flow is the product's rule #1 and must work without a PSP in the loop |
| Repository name: `tripsplit` | |

## 3. Architecture

```
backend/src/app/
  models|schemas|services|repositories|routes/   (layer-first, from the skeleton)
    trips          Trip + Member (invite link, trip state)
    proposals      3 packages generated by the LLM + Vote
    contributions  each member's share (PaymentProvider port; FakePayments first, Stripe later)
    bookings       Booking (train|stay|activity) + BookingRun (agent run state, artifacts)
    events         the group "chat" feed — everything the agent says and does
  agent/           the browser-driving loop: browser/observe/act/recover/planner/vault/skills/trajectory/runner
                   runs write var/agent/runs/<id>/{NN.png,live.jpg,status.json,result.json}
  ai/              ChatModel port + adapter — package generation, re-planning
frontend/src/
  routes/   /  /login  /register  /t/$tripId  /t/$tripId/join  /t/$tripId/pay  /t/$tripId/live
  features/ trips  proposals  contributions  bookings  agent-live   (polling via TanStack Query, 2s)
```

### Trip state machine

```
collecting -> proposing -> voting -> paying -> booking -> booked -> disrupted -> rebooking -> done
```

**Rule #1 lives in code — in the service, not in the UI:** `booking` starts ONLY when the sum
of paid contributions equals the trip total.

### Key technical decisions

- **The agent runs as a subprocess** (sync Playwright) started from asyncio. No task queue
  until parallel runs are actually needed (YAGNI).
- **The final "pay" click is a human's.** The agent reaches the summary (`stop_before_pay`),
  the UI shows the screenshot and the amount, the organizer clicks Approve, and the agent
  performs the last click.
- **Stretch: BLIK.** The UI asks for the code, the agent types it, the bank app confirms. This
  sidesteps 3-D Secure.
- **Disruption scene** = a dev endpoint `POST /trips/{id}/simulate-disruption` -> event "train
  delayed 2h" -> the agent proposes an alternative -> re-split -> rebooking.
- **`browser-harness` (CDP in the developer's Chrome) is a DEV tool** for writing supplier
  playbooks (`agent/skills/intercity.pl.md`, `booking.com.md`) by reconnaissance. The agent
  itself runs headless.

## 4. Work split (two people, after Phase 0)

| | Person A — "group & money" | Person B — "agent & booking" |
|---|---|---|
| Backend | Models `trips` / `proposals` / `contributions` / `events`; LLM package generation, voting, split; `PaymentProvider` port + `FakePayments` | `agent/` package + runner + live frames endpoint; `BookingRun` orchestration, approve-final-click, handoff |
| Recon | — | Playbooks `intercity.pl` / `booking.com` via CDP |
| Frontend | Trip room, vote cards, contributions screen | `/live` preview + Approve + simulate disruption |

**The seam between them:** the OpenAPI contract plus the `BookingRun` model, both agreed in
Phase 0.
